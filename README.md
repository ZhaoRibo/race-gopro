# race-gopro —— 从 GoPro 视频里挖出专业赛车遥测

拿 GoPro 拍卡丁车，把视频文件里那条遥测轨解出来，得到圈速、G 值、走线对比和逐弯
分析。不需要外加传感器，相机导出的原始 MP4 直接丢进来就行。

---

## 这个工具能干什么

| 功能                   | 具体内容                                             | 在哪看                                                           |
| ---------------------- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| **圈速**         | 每圈用时、最快圈、平均圈、标准差、稳定性评级         | 终端报表 · `dashboard.html` 第一张图 · `tables/laps.csv`   |
| **分段成绩**     | 3 个 sector 的用时、"理论最佳圈"、"连续分段最佳"     | 终端报表 · `tables/laps.csv`                                  |
| **G 值**         | 纵向（加速 / 刹车）与横向（转向）加速度，200 Hz      | `charts/gg_diagram.png` · `tables/telemetry.csv`            |
| **弯道分析**     | 每个弯的顶点速度、等效半径、刹车点位置及其逐圈一致性 | 终端报表 · `charts/corner_apex.png` · `tables/corners.csv` |
| **圈间时间差**   | 相对最快圈，时间具体丢在哪个弯                       | `charts/delta.png`（最有用的一张）                             |
| **走线对比**     | 各圈轨迹叠加，以及相对平均走线的横向偏差             | `charts/lap_lines.png`                                         |
| **赛道俯视图**   | 赛道形状、按速度着色、标出起点线与弯号               | `charts/track_map.png`                                         |
| **交互式看板**   | 上面所有内容合成一页，可勾选显示哪几圈               | `dashboard.html`                                               |
| **HUD 叠加视频** | 像转播那样把速度 / G 值 / 圈速烧进画面，也可以只给某一圈出片 | `<视频名>_hud.mp4`（整段）、`<视频名>_hud_lap8.mp4`（单圈） |

数字都是从 GoPro 视频文件里那条**独立的元数据轨道**读出来的，不是软件估算的：

```
GX010123.MP4
├── 视频轨   H.265 / H.264
├── 音频轨   AAC
└── gpmd      ← 就是它。GPS 10~18Hz + 加速度计/陀螺仪 200Hz
```

RaceChrono、Telemetry Overlay 这些专业圈速软件读的也是这条流。

## 快速开始

### 直接下载安装包（最省事）

到 [Releases](../../releases) 页面下载对应你系统的包，解压、双击就能用 ——
**ffmpeg 已经打在包里**，不用另外装任何东西。

| 你的电脑                                | 下载哪个                            |
| --------------------------------------- | ----------------------------------- |
| Mac（M1/M2/M3/M4，2020 年以后基本都是）  | `race-gopro-macos-arm64.zip`        |
| Windows 64 位                           | `race-gopro-windows-x64.zip`        |
| Intel 芯片的 Mac                        | 没有现成的包，用下面「从源码跑」那套 |

包里就是应用本体 + 一份「使用说明」。解压后：

- **macOS**：右键点「卡丁车遥测分析.app」→「打开」→ 再点一次「打开」。
- **Windows**：双击 `race-gopro\race-gopro.exe`。

**为什么要右键？** 应用没有签名（作者没买代码签名证书：苹果一年 99 美元）。
未签名的应用从网上下下来会被系统当成可疑文件，右键「打开」是告诉系统
"我知道它的来历"。**放行一次之后，以后就能直接双击了**。
Windows 上如果弹蓝色的「Windows 已保护你的电脑」，点「更多信息」→「仍要运行」。

打开之后：浏览器自动弹出（没弹就手动开 <http://127.0.0.1:8765/>）→
点「选择视频文件…」选一个 GoPro 原始 MP4 → 等它跑完 → 自动跳到看板。
结果写在视频旁边的 `<视频名>_out/`。关掉浏览器页面，程序自己退出。

出问题要看日志：macOS 在 `~/Library/Application Support/race-gopro/app.log`，
Windows 在 `%APPDATA%\race-gopro\app.log`。

### 不想碰命令行：双击 启动.app

在 Finder 里双击仓库根目录的 **`启动.app`**（第一次可能要右键→打开），
浏览器会自动弹出来：

1. **选视频** —— 点「选择视频文件…」弹系统文件框；也支持「浏览文件夹」和自己粘路径。
2. 自动分析，结果照旧写在**视频旁边**的 `<视频名>_out/`，不用指定目录。
3. 自动跳到看板 —— 出片、改起点线都在那一页里点。
4. **关掉浏览器页面，程序自己退出**，不用回来杀进程
   （也可以在 Dock 上右键它的图标 → 退出）。

它**不占用终端窗口**：出问题会弹个对话框告诉你，明细写在仓库根的
`.race-gopro.log` 里。

> 为什么是 `.app` 而不是更好做的 `.command`：`.command` 是让「终端」开个窗口、
> 用你的登录 shell 把路径"敲"进去执行，而 **oh-my-zsh 启动时那句
> 「Would you like to update? [Y/n]」会读走一个字符** —— 路径开头的 `/` 被吃掉，
> 就变成了 `Users/...` 这样的相对路径，报 `no such file or directory`。
> `.app` 由系统直接执行，不经过 shell，没这个问题。

命令行那条路**完全没变**，两个入口共用同一条流水线，文件产出一模一样：

| 想干的事              | 双击                  | 命令行                                              |
| --------------------- | --------------------- | --------------------------------------------------- |
| 分析一个视频          | `启动.app` → 选文件 | `.venv/bin/python analyze.py 视频.MP4`            |
| 出单圈 HUD / 改起点线 | 同上（页面里的按钮）  | `.venv/bin/python analyze.py 视频.MP4 --serve`    |
| 批量 / 写脚本         | —                    | 命令行（可以自己拼循环）                            |
| 只想要文件不想开服务  | —                    | 不加 `--serve` 就是纯命令行                             |

两种方式做的事只有一点不同：双击是**一次一个视频**、结果会在页面里给你看；
要批量处理、或者嵌进自己的脚本里，还是用命令行。

### 先确认环境

|                  | 要求                                              | 怎么弄（macOS）                          |
| ---------------- | ------------------------------------------------- | ---------------------------------------- |
| **Python** | 3.9 以上（开发环境用的是 3.13）                   | 系统自带；没有就 `brew install python` |
| **FFmpeg** | **必须有** —— 遥测轨要靠它从 MP4 里抽出来 | `brew install ffmpeg`                  |
| **视频**   | 相机导出的**原始** MP4，没被任何软件转码过  | 见 [拍摄时要注意的事](#拍摄时要注意的事)    |

先确认 FFmpeg 装好了：

```bash
ffmpeg -version
```

### 四步跑起来

```bash
# 1. 装依赖（只需要做一次）
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 2. 先自检一下环境和算法有没有问题
.venv/bin/python analyze.py --selftest

# 3. 分析你的视频
.venv/bin/python analyze.py ~/Movies/GX010123.MP4

# 4. 想要带 HUD 的叠加视频（耗时较长，建议先只做一段）
.venv/bin/python analyze.py ~/Movies/GX010123.MP4 --overlay --overlay-range 60,180
```

没有视频也能先看效果：

```bash
.venv/bin/python analyze.py --demo
```

会生成一条合成赛道的数据，把整条输出链路（报表、图表、看板、HUD 视频）都跑一遍。

结果都在**源视频旁边**的 `<视频文件名>_out/` 目录里 —— 视频拷到哪儿，结果就在哪儿，
不会散在别处。（加 `-o 目录` 可以改成放到指定位置；用 `--demo` 时默认 `./out/`。）

## 拍摄时要注意的事

这几条直接决定数据能不能用，比后期任何处理都重要：

| 事项                               | 说明                                                                                                                                                                                                              |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **相机必须刚性固定在车身上** | 装在前整流罩、座椅后方都行。**绝对不要用头盔支架** —— 相机随头部转动，等于安装角一直在变，G 值就没法算了。                                                                                                |
| **必须开启 GPS**             | HERO11 默认开启。录制时要在室外、起步前给相机 30 秒以上搜星时间，否则前几十秒没有轨迹。                                                                                                                           |
| **不要用剪辑软件重新导出**   | 任何转码（GoPro Quik、剪映、Final Cut）都会把 `gpmd` 元数据轨丢掉，剩下的只有画面。要分析就必须用相机导出的**原始 MP4**。                                                                                 |
| **镜头朝向尽量摆正**         | 程序会自动标定安装角，歪 20° 以内都能算准；歪太多会降低精度。                                                                                                                                                    |
| **长视频会分段**             | GoPro 录久了会把文件切成 `GX01xxxx.MP4` 多段，每段的遥测时间轴都从 0 开始，不能直接拼。先合并：<br>`printf "file '%s'\n" GX01*.MP4 > list.txt`<br>`ffmpeg -f concat -safe 0 -i list.txt -c copy merged.MP4` |

## 结果放在哪

一次分析会产出十几个文件，按用途分放在三个地方。下面以 `video/GX010046.MP4` 为例：

```
video/GX010046_out/          ← 就在源视频旁边
├── dashboard.html          ← 双击打开，圈速 / G 值 / 弯道分析全在里面
├── GX010046_hud.mp4        ← 带 HUD 的叠加视频（需要加 --overlay）
├── charts/                 图表
│   ├── lap_times.png
│   ├── speed_trace.png
│   ├── delta.png
│   ├── gg_diagram.png
│   ├── track_map.png
│   ├── lap_lines.png
│   └── corner_apex.png
└── tables/                 数据表
    ├── laps.csv
    ├── corners.csv
    ├── laps_aligned_speed.csv
    ├── laps_aligned_glat.csv
    ├── telemetry.csv
    └── analysis.json
```

### 第一次用，按这个顺序看

1. **`delta.png`** —— 相对最快圈的时间差。曲线往上爬的那一段，就是你丢时间的地方。
   先知道"问题在哪个弯"，后面才有意义。
2. **`corner_apex.png`** —— 逐弯顶点速度对比。哪个弯的柱子差得最多，就是最该练的弯。
3. **`lap_lines.png` 右半边** —— 那个弯上各圈的走线差多少，差在入弯还是出弯。
4. **`gg_diagram.png`** —— 离轮胎的抓地极限还有多少余量。
5. **`dashboard.html`** —— 上面这些都在一页里，还能勾选只看某几圈。

等节奏稳了、想横向比车（换了车或换了胎）再看 **速度增量**，见 [G 值](#g-值)。

**`dashboard.html` 是唯一入口**，故意放在最外层 —— 结论、可交互的图表、
逐圈明细表都在这一页里，页尾再列出所有可下载的文件。

页面从上到下的顺序：**赛道俯视图**（定计时线）→ 单圈 HUD 视频 → **圈选择器**
→ 圈速分布 → 速度—距离曲线 → 时间差 → G-G 图 → **每圈走线** → **每圈走线偏差**
→ 逐弯顶点速度 → 逐圈明细。

把赛道图摆在最前面是有意的：**先定下计时线在哪，再谈"看哪几圈"才有意义** ——
计时线一挪，圈号、圈速、最快圈全都跟着变，所以它得排在任何按圈拆的东西前面。

> **圈选择器**（吸顶，滚到哪张图都能随手勾）用勾选框控制显示哪几圈，另配
> 「全选 / 全不选 / 只看最快圈 / 最快 3 圈 / 最快 5 圈」五个快捷按钮。
> 它**同时作用于所有「每圈一条线」的图表**（速度—距离曲线、时间差、每圈走线、
> 每圈走线偏差）；圈速分布 / G-G 图 / 赛道俯视图不受影响（它们不是按圈拆的）。
> 点任意一张图的**图例**效果完全一样 —— 和图例共用同一份状态，不会两边不同步。

> 「每圈走线」和「每圈走线偏差」是一对：前者把各圈轨迹叠在一起，后者把各圈
> 相对平均线的横向偏移单独抽出来。**看差异要看后者** —— GPS 单点噪声就有 1~3 米，
> 而真实走线差异往往只有零点几米，叠加图上噪声会把差异盖住。

图表和数据表各开一个子目录，是因为一次分析会产出十几个文件，平铺在一层里，
每次都要在一堆 CSV 中间找那张想看的图。分开之后，要发朋友圈的图去 `charts/`，
要自己做透视表的去 `tables/`。

### 数据表 `tables/`

| 文件                       | 内容                                                                                                                                                                          |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `telemetry.csv`          | 全场逐点数据：时间、经纬度、速度、航向、纵向 G、横向 G。可以直接拖进 Excel 或 `pandas.read_csv`                                                                             |
| `laps.csv`               | 每圈一行：圈时、与最快圈的差、各分段用时、极速/最慢速、峰值横向/刹车/加速 G、`speed_gain_ms`（速度增量）、`accel_time_pct`（纵向 G 为正的时间占比，**不是全油门**） |
| `laps_aligned_speed.csv` | **距离对齐**的宽表：每一列是一圈，每一行是距起点线 N 米处的速度。想自己画对比图就用它                                                                                   |
| `laps_aligned_glat.csv`  | 同上，横向 G                                                                                                                                                                  |
| `corners.csv`            | 弯道 × 圈 的明细：顶点速度、进出口速度、最大横向 G、刹车点位置                                                                                                               |
| `analysis.json`          | 上面所有内容的结构化版本，方便喂给别的工具                                                                                                                                    |

> 加了 `--no-csv` 就不会生成 `tables/`，看板页尾对应的入口也会自动消失（不会留死链接）。

> **关于 `accel_time_pct`（加速时间占比）**：它统计的是"纵向 G 为正"的时间占一圈的百分比。
> 早期版本把它叫作"全油门时间占比"，**那是错的** —— GoPro 测不到油门开度或刹车压力，
> 而且卡丁车漂移时纵向 G 里混着一项侧滑贡献 $-v\omega\sin\beta$（能到 ±0.8 g），
> 与油门开度没有对应关系。这个字段现在只表示"加速过程占了多久"，别当油门看。
> HUD 里同理不做油门/刹车指示。
>
> **关于峰值 G**：表里所有带“峰值”的列都先按时间平滑了 1 秒（见
> [峰值 G 一律先按时间平滑 1 秒](#峰值-g-一律先按时间平滑-1-秒)）。
> **想要横向比车，看 `speed_gain_ms` 而不是峰值 G** —— 它是有精确物理答案的量。

### 图表 `charts/`

| 文件                | 看什么                                                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `lap_times.png`   | 圈速柱状图。柱子高度差 = 你的稳定性                                                                                                              |
| `speed_trace.png` | 速度—距离曲线，所有圈叠在一起。曲线越重合说明走线越一致                                                                                         |
| `delta.png`       | **最有用的一张**。相对最快圈的时间差：曲线上涨 = 正在丢时间，下降 = 正在追回来。一眼看出是哪个弯的问题                                     |
| `gg_diagram.png`  | G-G 图（摩擦圆）。散点外围的那圈红线就是这条轮胎的抓地力极限                                                                                     |
| `track_map.png`   | 赛道俯视图，按速度着色，标出起点线和各弯。**画的是所有有效圈的平均走线**，不是某一圈                                                       |
| `lap_lines.png`   | **每圈走线对比**。左边把各圈轨迹叠在一起，右边把每圈相对平均走线的横向偏差单独抽出来（+ 左 / − 右）。想看走线差异就看右边那一栏，原因见下 |
| `corner_apex.png` | 逐弯顶点速度对比。柱子差得越多，说明这个弯开得越不稳定                                                                                           |

> **为什么走线差异要看 `lap_lines.png` 的右边**：GPS 单点噪声就有 1~3 米，而真实
> 走线差异往往只有零点几米到一两米 —— 在左边那种叠加图上，**噪声会把差异盖住**，
> 看起来"所有圈都跑在同一条线上"。右边那一栏把各圈相对平均走线的横向偏移
> **单独抽出来画**（横轴 ±4 米），差异才看得出来。实测最快圈基本贴着 0 线走，
> 慢圈在几个弯里有 1~4 米的偏差。

### 最外层

| 文件                 | 说明                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------ |
| `dashboard.html`   | 网页看板，**分析的入口**。双击就能打开，数据已内嵌，不需要服务器。图表都是可交互的（点图例可隐藏某圈） |
| `<视频名>_hud.mp4` | 带 HUD 的叠加视频（需要加 `--overlay`）                                                                    |
| `<视频名>_hud_lap8.mp4` | 单圈 HUD 视频，在看板里点出来的（见下）                                                              |

**HUD 里显示什么**（四个角，中间留给你看路）：

| 位置         | 内容                                                                     |
| ------------ | ------------------------------------------------------------------------ |
| **左上**   | 圈号 / 本圈计时 / 与最快圈的差距（快是绿、慢是红）/ 全场最快圈           |
| **右上**   | 本圈速度曲线，叠一条最快圈作参考；竖线标出现在跑到哪儿了                 |
| **左下**   | 纵向 G 指示条（向上绿 = 加速，向下红 = 刹车）+ G-G 圆盘和横向 G 数值 |
| **右下**   | 当前时速                                                                 |

> **为什么没有油门/刹车指示**：GoPro 测不到油门开度或刹车压力。任何“油门/刹车”
> 都只能从纵向 G 硬换算，而卡丁车漂移时车体系纵向加速度里混着一项
> $-v\omega\sin\beta$（$\beta$ 是侧滑角，能到 ±0.8 g），跟油门刹车毫无关系 ——
> 弯中明明在加油，指示条却在乱跳。与其给个骗人的读数，不如直接显示纵向 G 本身。

### 单圈 HUD 视频：在看板里点一下就出

想看某一圈的叠加视频，不用记命令 —— 看板上有一栏「单圈 HUD 视频」，选一圈点按钮，
就会生成**这一圈前后各留 5 秒**的片段（过线那一瞬间才不会被切掉），文件叫
`<视频名>_hud_lap<圈号>.mp4`，跟看板放在一起，生成完直接在页面上点开就能播。
页面底部的逐圈明细表每行末尾也有一个「出片」按钮，效果一样。

下拉里第一项是**整段视频** —— 把全片都烧上 HUD，文件叫 `<视频名>_hud.mp4`
（和命令行 `--overlay` 出来的那个是同一个名字）。这一项会跑很久，所以选它的时候
下面会先把粗估写出来：以这台机器的 11 分钟、2704×2028 素材为例，**约 20 分钟，
输出约 4.5 GB**。估的是编码时间，不是画 HUD 的时间。

前提是**看板得从本地服务打开**，不能双击 html 文件 ——
双击 `启动.app` 跑一遍，或者手动 `--serve`，两者等效：

```bash
# 带 --serve 跑一次：分析照常跑完，然后不退出，把看板挂到本地端口上
.venv/bin/python analyze.py video/GX010047.MP4 --serve

# 用它打印的地址打开看板（默认 8765 端口）
#   http://127.0.0.1:8765/
```

为什么非得起服务：看板是单个静态 HTML，双击打开时跑在浏览器的沙箱里，
**没有任何办法调用 ffmpeg**。所以出片这件事只能由浏览器外面的进程干，`--serve`
起的就是这个进程 —— 只监听 127.0.0.1，不联网。顺带的好处是生成的视频能直接在
页面里播放，`charts/` 和 `tables/` 那些链接也由同一个服务提供。

不想起服务也没关系：按钮会变灰并提示等效的命令行做法，自己指定时间范围就行
（`--overlay-range` 用的秒数和看板上显示的是同一套）：

```bash
.venv/bin/python analyze.py video/GX010047.MP4 --overlay --overlay-range 400.6,459.0
```

出一圈大概要几分钟，慢在编码上（用的是源视频分辨率，不是画 HUD）。嫌慢就加
`--overlay-preset veryfast` —— `--serve` 会把这个设置用在网页出的片上。

### 计时线也能在看板里直接挪

需要本地服务（双击 `启动.app` 或手动 `--serve`，等效）。赛道俯视图下面有个
**「选择起点线…」按钮**，点开才会出现滑动条 —— 平时是收着的，不动它就不占地方。
滑动条的值就是视频时刻：

1. 拖滑动条（或者用鼠标点一下滑动条，再按 **← → 逐帧**微调），
2. 下方会显示**那一刻的画面**，看画面里的车压没压到发车线，
3. 对上了就点「用这一帧当起点线」，整场重新切圈 —— 圈速表、图表、CSV、看板
   全部重算并覆盖。**重算完选取面板会自动收起来**，页面随即刷新。

不满意就再滑一次，或者按「恢复自动」退回自动搜到的那条线。

几个细节：

- **为什么要看画面**：起点线的定义就是"车压过发车线的那一瞬"，而这一刻在赛道
  图上点不出来 —— 图上一个像素代表好几米，点哪儿都差得远。看画面则一眼就能判断
- 键盘：`←` `→` 走一帧，按住 `Shift` 走 1 秒，`PageUp` / `PageDown` 走 10 秒，
  `Home` / `End` 直接到片头 / 片尾，`Enter` 等于点确定
- 你选的时刻会被**吸附到最近的遥测采样点**（GPS 是 10 Hz，所以精度是 0.1 秒），
  位置必须落在车真走过的点上，线飘在赛道外面没意义
- 过线方向由服务端自动定（按那一点的行驶方向），不用自己管
- 图上那条**青色的线**就是服务端算出来的结果，不是前端自己估的；旁边的
  「距当前计时线 N 米」和画面下方的「第 N 帧 / 遥测点时刻」都是给你核对用的
- 取一帧要**约 0.4 秒**（GoPro 的关键帧间隔是 1 秒，取中间某一帧得从上个关键帧
  解起，等于每帧都要解 60 帧 4K），所以拖的时候画面会略慢半拍，松手后立刻跟上。
  服务端缓存了最近取过的帧，来回翻帧不会重算
- 收起之前选的时刻**不会丢**：再打开还是停在原处，不用从头滑
- **出片任务在跑的时候不能改计时线** —— 圈号会变，正在生成的片段会和新的圈号对不上
- 命令行那条路照旧：`--list-gates` / `--gate-time` / `--gate-index` / `--gate 纬,经`
  随时能用，两种方式效果一样（都走 `laps.compute_lapset`）

## 怎么读这些数据

### 圈速

```
最快圈        52.030  (第 8 圈)
平均圈        52.415
标准差        0.378 s    稳定性: 0.72% —— 很稳定
```

稳定性用**变异系数**（标准差 ÷ 平均圈速）衡量。赛车上的经验值：

| 变异系数  | 含义                                     |
| --------- | ---------------------------------------- |
| < 0.5%    | 职业水准，几乎每一圈都一样快             |
| 0.5% ~ 1% | 很稳定                                   |
| 1% ~ 2%   | 较稳定                                   |
| 2% ~ 4%   | 一般，还有提升空间                       |
| > 4%      | 波动较大，先把节奏稳定下来比找极限更有效 |

出场圈（从维修区出来的第一圈）会自动识别并排除在统计之外，表里用 `*` 标记。

### 理论最佳圈 vs 连续分段最佳

- **理论最佳圈** = 三个分段各自的历史最好成绩之和。
  这个数字**实战中跑不出来** —— 三个分段的最好成绩可能来自三圈互相矛盾的跑法。
- **连续分段最佳** = 相邻三个分段（也就是完整的一圈）用时之和的最小值。
  这个是**真实可达**的：说明你已经在某一圈做到了。

两个数字之间的差距，就是你"知道怎么开但还没连起来"的潜力。

### 弯道表

```
弯 │ 方向 │ 起点 │ 顶点 │ 长度 │ 半径 │ 顶点速度 │ 第5圈 │ 第6圈 │ 速度波动 │ 刹车点离散
2  │   右 │  160 │  170 │   18 │    4 │     27.0 │  26.9 │  27.8 │      1.9 │       21.2
```

- **半径**：由 `a = v²/R` 反推的等效半径。半径 4 m 就是那种一档掉头的发夹
- **顶点速度**：这个弯里速度最低的那一点。卡丁车没有下压力，弯速几乎完全由轮胎摩擦圆决定，所以这是"敢不敢开"最直接的指标
- **速度波动**：同一个弯各圈顶点速度的标准差。**这个数字大 = 这个弯还没形成稳定跑法**，是最该花时间练的地方
- **刹车点离散**：各圈刹车点位置的标准差（米）。偏大说明刹车点每圈都在变，通常是因为在边刹车边找弯心

### Delta 曲线（相对最快圈的时间差）

横轴是距起点线的距离，纵轴是"这一点上比最快圈慢了多少秒"。

**曲线中途出现负值是正常的**：那说明你在赛道的那一段实际上**比自己的最快圈还快**，
只是后来又丢回去了。曲线上升 = 正在丢时间，下降 = 正在追回。
这正是 delta 图的价值 —— 它告诉你时间是在哪个弯丢掉的。

**但在终点处必须为正**：终点处两圈的差距就是圈时差，一圈不可能真的比最快圈还快。
如果你看到终点附近出现负值，那是里程对齐出了问题（本项目早期版本就有这个 bug，
原因见下文"圈与圈之间按中心线弧长对齐"）。

### 圈速和官方计时为什么会有零点几秒的差

圈速是在**自动识别的起点线**上测的。这条线不一定就是官方的计时线，
而赛车场上任意一点的圈速只在"每一圈都跑得一模一样"时才相等。

严格推导一下：设官方计时线在赛道上的位置为 0、自动识别的线在位置 q，
那么自动线的第 k 次到第 k+1 次过线之间的间隔是

$$
\Delta t_k = T_k + \big(\text{head}_{k+1} - \text{head}_k\big)
$$

其中 $T_k$ 是官方第 k 圈的时间，$\text{head}_k$ 是从官方线跑到位置 q 所用的时间。
所以**只有当你这一段跑得和上一圈一样快时，两者才相等**；
某一圈在 q 之前那段有失误，差值就会表现出来。

实测：同一份数据 9 圈里 8 圈和官方计时差在 **±0.1 s** 以内，
只有一圈差了 0.55 s（就是那一圈在 q 之前那段丢了时间）。

要对齐官方计时，可以从赛道图上读一个官方计时线的坐标用 `--gate 纬度,经度` 指定，
也可以用 `--gate-time 秒` 指定"官方计时线那一次过线发生的时刻"。

### 起点线是怎么选的（以及怎么手动改）

关键认识：**赛道上任意一点都可以当起点线**，圈速就是"同一位置连续两次经过之间的
时间"。所以不存在"唯一正确答案"，但**选得好不好会实实在在地影响结果**：

- 线开在赛道**自己旁边**（另一段赛道的附近）→ 同一圈会被穿两次，圈速直接算错
- 线开在**弯道**上 → 车是斜着走的，过线瞬间的位置抖动更大

工具按下面顺序挑：

1. 沿**连续行驶的那一段**轨迹每 3 米撒一个候选点
   （不能拿整段录制去算 —— 起步前/收车后停车的样本会挤在轨迹同一点，
   算圈时自相关时会把"一圈"那个峰彻底盖住，实测算出 9.9 s，真实是 48.6 s）
2. 每个候选点过**三关**：圈时合理（8~300 s）、圈时一致、**每圈行驶距离一致**
   （最后一条是抓"线开在赛道旁边"最硬的判据：一旦漏穿/多穿，每圈距离会变成
   半圈或两圈，离散度立刻爆掉）
3. 筛掉**偏僻度**不足的（偏僻度 = 这条线离"同一圈里赛道其它部分"最近有多远）
4. 剩下的里**优先选转弯量最小的**（即最靠直道的），同样笔直时取过线最早的

> **为什么先看直道**：赛道上的起点线常规都放在直道上 —— 裁判位、发车格、
> 官方计时线都在直道边。所以"这块直不直"（前后各 30 米内车的总转向角）
> 比"离别的赛道部分有多远"更贴近实际。
>
> 这一条是**用户提的**，实测效果很明显：加上之后圈速标准差从 0.79 s 降到 0.419 s，
> 和官方计时表的 0.42 s 几乎完全一致，且圈数也对上了。

不满意就手动换一条，三种方式（只能用一个）：

```bash
# 1. 先看有哪些候选（按"直道优先"排序，带转弯量 / 偏僻度 / 圈时变异）
python analyze.py 视频.MP4 --list-gates

# 2. 挑第 N 条
python analyze.py 视频.MP4 --gate-index 3

# 3. 用自己的时刻：视频里过线那一帧的秒数（最容易上手，不用读经纬度）
python analyze.py 视频.MP4 --gate-time 200

# 4. 直接给经纬度（从 track_map.png 上读）
python analyze.py 视频.MP4 --gate 22.8754,113.2664
```

手动的线也会自动补上偏僻度 / 圈数 / 圈时变异系数，方便你判断换得对不对。

### G 值

约定：**横向 G 正值 = 左转**（ISO 8855 车辆坐标系），**纵向 G 正值 = 加速、负值 = 刹车**。

横向 G 的绝对值没有太多意义，有意义的是：

- **同一辆车同一条胎，G 越大说明轮胎被用得越充分**。卡丁车通常能到 1.5～2.0 g
- **G-G 图上的形状**：如果数据点集中在一个椭圆里而很少碰到椭圆外沿，说明你离极限还有余量

> **想比车，看「速度增量」而不是峰值 G。** 表格里带"峰值"的列已经自动做过
> 1 秒平滑（[为什么](#峰值-g-一律先按时间平滑-1-秒)），但仍然只是**峰值**；
> 而 `速度增量` 是有精确物理答案的积分量，最能反映马力差异。

G 值的重力扣除用 GoPro 自己记录的 `GRAV` 流逐时刻完成。原理和取舍见
[G 值提取](#2-g-值提取这一步决定了-g-值对不对)。

## 自检

`--selftest` 会跑**两组检查**，都不需要真实视频：

**GPMF 二进制解析器**：手工按 GoPro 格式规范构造一段字节流，再喂给解析器，
逐项核对解出来的数值、采样率、单位、缩放是否正确。覆盖了大端序读取、
容器嵌套、`unit_size=0` 的固件差异、以及 71.6 分钟的时间戳回绕。

**G 值提取**：生成一段合成驾驶数据，其中**加速度、重力方向、相机安装角都是已知的**
（故意把相机设成俯仰 −18°、滚转 +6°、偏航 +4° 的歪装，`GRAV` 也加上零点几度的
残余漂移和幅值抖动）。然后：

- 检查识别出的**轴变换是否为恒等**（合成数据里 `GRAV` 与 `ACCL` 本来就同轴系，
  识别错了会立刻暴露 —— 这条能直接抓出轴识别逻辑被改坏）
- 检查解出的重力大小是否接近 9.807
- 把算出的 G 值与真值逐点比对，要求相关系数 > 0.85
- 检查横向 G 的**符号约定**（正 = 左转）是否正确

```
  GPMF 二进制解析器 : 通过 ✓
  G 值提取          : 通过 ✓
```

解析器的回归测试也可以单独跑：

```bash
.venv/bin/python -m tests.test_gpmf
```

`tests/test_paths.py` 是另一类检查：**文件名在 Windows 上能不能用**。
macOS 允许文件名里带反斜杠、末尾带空格，Windows 不允许 —— 而这种问题本地毫无
征兆，只会在 CI 的 Windows 任务 checkout 那一步炸掉（连一行代码都跑不到）。
改完东西顺手跑一下：

```bash
.venv/bin/python -m tests.test_paths
```

`tests/test_no_console.py` 验的是打包版的启动条件：Windows 的窗口模式下
`sys.stdout` / `sys.stderr` 是 `None`（不是空流），导入期任何一句 `print` 或
`.isatty()` 都会把程序打死。这个坑在 macOS 上永远复现不出来，所以测试干脆在
子进程里把两个流置成 `None` 再导入一遍：

```bash
.venv/bin/python -m tests.test_no_console
```

`tests/test_subprocess_hygiene.py` 盯着子进程怎么写：窗口模式下 Windows 会给**每个**
子进程开一个新的控制台窗口，而这个程序一分析视频就反复调 ffmpeg，于是看板上每点
一下就闪一个黑框。修法是统统走 `rapp/subproc.py`（它会带上 `CREATE_NO_WINDOW`），
而这个标志只在 Windows 上生效、macOS 上漏了看不出来，所以得靠测试盯着：

```bash
.venv/bin/python -m tests.test_subprocess_hygiene
```

`tests/test_hud_fonts.py` 盯的是 HUD 的字体：**字大不大，完全取决于能不能加载到
一个真正的字体文件**。一个都加载不了时，PIL 会退回内置位图字体（固定 11 px、
不能缩放），画在 4K 画面上就是"字小到几乎看不见"。

```bash
.venv/bin/python -m tests.test_hud_fonts
```

想用 pytest 的话得先装（它不在运行依赖里）：

```bash
.venv/bin/pip install pytest
.venv/bin/python -m pytest tests/
```

## 已知限制

**说在前面：GoPro 是消费级设备，不是 Racelogic VBOX。**

| 限制                               | 影响                                       | 怎么缓解                                                           |
| ---------------------------------- | ------------------------------------------ | ------------------------------------------------------------------ |
| GPS 只有 10~18 Hz，定位误差 1~3 m | 圈速分辨率约 0.1 s；赛道图上轨迹有可见抖动 | 够用来分析自己的提升趋势，别指望和官方计时完全一致                 |
| 起步阶段 GPS 可能还没定位          | 开场几十秒没有轨迹，这些圈无法分析         | 录制前给相机 30 秒以上搜星时间                                     |
| 加速度计有零偏和温漂               | G 值可能有百分之几的绝对误差               | 相对比较（同一场次内的圈与圈对比）是准的                           |
| 相机必须刚性固定                   | 头盔支架会让数据完全不可用                 | 装在车身 / 整流罩上                                                |
| 剪辑或转码会丢失遥测轨             | 文件里没有 `gpmd` 流，直接报错           | 只用相机导出的原始 MP4                                             |
| 一次只分析一个视频                 | 给了多个也只取第一个（会打提示）           | 多段视频先用 ffmpeg 合并，见 [拍摄时要注意的事](#拍摄时要注意的事)    |
| 卡丁车赛道旁常有建筑               | GPS 多路径误差偏大，个别定位点会飞         | 程序会自动剔除异常定位点并给出警告                                 |
| 自动识别的起点线不等于官方计时线   | 个别圈的圈速会和官方计时差零点几秒         | 用 `--list-gates` 看候选，再用 `--gate-time 秒` 对到官方计时线；或者起 `--serve`，在看板的滑动条上找到压线那一帧直接挪 |
| 弯道数量依赖横向 G 峰值识别        | 弯道极密的场地可能多切或漏切               | 调 `rapp/analysis.py` 里的 `CORNER_MIN_SEPARATION`             |

另外：卡丁车短赛道的弯道比较密集，程序按"横向 G 超过 0.25 g 且持续 8 米以上"来
划分弯道。特别近的连续弯（比如蛇形弯）可能会被合并成一个，可以把
`rapp/analysis.py` 里的 `CORNER_MAX_GAP` 调小。

## 常见问题

**Q: 跑完了，文件在哪？**

默认在**源视频旁边**的 `<视频名>_out/` 目录里（视频在哪它就在哪）。想放到别处加
`-o 目录`。命令行最后一行会打印完整路径。先打开里面的 `dashboard.html`。

**Q: 我有好几个视频（或者一个视频被切成了多段），能一起分析吗？**

不能，一次只取第一个文件。GoPro 长时间录制会把文件切成 `GX01xxxx.MP4`，
每段的遥测时间轴都从 0 开始，拼不起来。先用 ffmpeg 合并成整场，做法见
[拍摄时要注意的事](#拍摄时要注意的事)。

**Q: 报错"没有可用的 GPS 数据"**

录制时没开 GPS，或者视频被转码过。用 `--list-streams` 确认一下文件里有没有遥测轨。

**Q: 报错"没能找到合适的起终点线"**

按提示的三种原因排查。也可以先用 `--list-gates` 看看有哪些候选位置，
再用 `--gate-index N` 或 `--gate-time 秒` 手动指定。

**Q: 圈速明显不对（比如只有实际的一半，或者标准差很大）**

起终点线开在了赛道自己旁边。看 `track_map.png` 上黑线的位置，
如果它靠近赛道的另一段，就用 `--list-gates` 换一条（选"转弯量小、偏僻度大"的）。
最直观的办法是起 `--serve`，在**起点线滑动条**上滑到车压过发车线的那一帧
（看下方的画面确认），按「用这一帧当起点线」立刻能看到新圈速
（详见 [计时线也能在看板里直接挪](#计时线也能在看板里直接挪)）。

**Q: G 值看起来不对 / "G 值一致性" r 很低**

先检查相机是不是刚性固定在车身上（最常见的原因是装在了头盔上）。
其次确认支架没松动。`--selftest` 通过说明算法本身没问题。
另外留意：**单圈最大 G 不可靠**，别拿它下结论 —— 见
[G 值](#g-值) 里的说明。

**Q: HUD 视频要跑很久**

慢的是 ffmpeg 编码，不是画 HUD。实测（2704×2028、preset medium）编一帧约 51 ms，
画一帧 HUD 只要约 3 ms —— 等于**一秒素材要花约 3 秒机器时间**：30 秒的片段约 1.5 分钟，
11 分钟的整段约 34 分钟，文件还会到 GB 级。

按性价比排下来：

1. `--overlay-range 起,止` 只做关心的那几圈 —— 按比例省，最有效
2. `--overlay-preset veryfast` —— 约快 40%，画质基本看不出差别
3. `--overlay-crf 23` —— 文件小一截，编码也略快

`--overlay-fps` 基本没用：实测 15 降到 5 fps 只快了 1 秒。因为输出的帧率跟的是
源视频（59.94 fps），HUD 少刷几次并不会让输出少编几帧。

**Q: 看板上「生成 HUD 视频」按钮是灰的，或者点了没反应**

看板必须从本地服务打开，双击 html 文件不行 —— 浏览器不允许静态页面自己调 ffmpeg：

```bash
.venv/bin/python analyze.py 你的视频.MP4 --serve
# 然后用它打印的地址打开看板（默认 http://127.0.0.1:8765/）
```

或者干脆双击 `启动.app`（同一个服务，只是多了个选视频的首页）。

详见 [单圈 HUD 视频](#单圈-hud-视频在看板里点一下就出)。

**Q: 双击启动的，怎么用完关掉？**

什么也不用做 —— **关掉浏览器页面就退了**。也可以在 Dock 上右键它的图标 → 退出。
出片正在跑的时候关页面不会掐掉它，程序会等出片写完再退。

**Q: 提示「端口 8765 已经被占用」**

大概率是上一次还开着（程序自己会打开地址）。直接用
<http://127.0.0.1:8765/> 就行；确实想重开一个就加 `--port 8766`。

**Q: 双击 `启动.app` 没反应 / 提示"未验证的开发者"**

macOS 对从压缩包解出来的 app 会拦一下：右键点它 → 打开 → 再确认一次就好。
还是不行的话看仓库根的 `.race-gopro.log`，那里有完整报错；也可以在终端里
直接跑 `.venv/bin/python -m rapp.app`，报错会直接打在屏幕上。

**Q: 双击后弹出一个终端窗口，里面写 `no such file or directory: Users/...`**

那是旧版的 `启动.command` 被 **oh-my-zsh 的更新提示吞掉了路径开头的 `/`**
（详见 [双击 启动.app](#不想碰命令行双击-启动app)）。现在改用 `启动.app` 了，
不会再碰到。顺手把 oh-my-zsh 更新一下（终端里跑 `omz update`）也能消掉那个提示。

**Q: 下载的安装包打开时说"来自身份不明的开发者"**

应用没有签名（见 [直接下载安装包](#直接下载安装包最省事)）。macOS 上右键点它 →
「打开」→ 再点一次「打开」；Windows 上点「更多信息」→「仍要运行」。
放过一次之后就不会再问了。

## 打包发 Release（维护者看）

普通使用者用不到这一节。想自己出一个"下载解压就能用"的包时看这里。

```bash
.venv/bin/pip install -r packaging/requirements.txt   # PyInstaller（只装一次）
.venv/bin/python packaging/build.py
```

跑完在 `dist/` 下拿到 `race-gopro-macos-arm64.zip`（或 Windows 上的
`race-gopro-windows-x64.zip`），传上去就能当 Release 资产。

**Windows 的包只能在 Windows 上打** —— PyInstaller 不做交叉编译。所以正式发版走
CI：推一个 `v*` 标签（例如 `v0.1.0`），`.github/workflows/build-app.yml` 会在
macOS 和 Windows 上各跑一次，自动把两个包挂到 Release 上。也可以在 Actions 页面
手动触发，那样就只留 Artifacts、不发 Release。

发版的完整步骤（版本号只有一处要改：`packaging/build.py` 里的 `VERSION`）：

```bash
# 1. 改 packaging/build.py 里的 VERSION
# 2. 提交
git add -A && git commit -m "发 v0.1.1"
# 3. 打标签 —— 标签名和 VERSION 保持一致，出问题好排查
git tag -a v0.1.1 -m "v0.1.1"
# 4. 分支和标签一起推 —— 只推分支不会触发打包
git push origin main v0.1.1
```

推完去 Actions 看进度（两个平台加起来 5～15 分钟）。**两个 job 都绿了才会出
Release**：任意一个失败，`release` 那一步会被直接跳过，Release 就不会出现 ——
所以别看到"有运行记录"就以为成了。

CI 上挂掉怎么查：Actions → 那次运行 → 点红色那个 job → 展开失败的那一步。注意
**日志要登录才能看**，公开仓库也一样，所以命令行里 curl 那个日志接口只会返回 403。

几个不要改回旧做法的点：

- **ffmpeg 是打进包里的**（`packaging/build.py` 自动下载各平台的静态构建）。
  千万别用 Homebrew 装的那个：它是动态链接的，拷进包里换台机器就废了。
  各平台来源：macOS arm64 用 osxexperts（文件名带版本号，所以是去首页现查的）、
  Intel Mac 用 evermeet、Windows 用 gyan.dev。必须带 `libx264`，出片要靠它。
- **matplotlib 的字体缓存也会预建好打进包**。不预建的话，用户第一次启动要花
  十几秒扫系统字体，而这十几秒界面上什么都没有 —— 看起来就是"双击了没反应"。
  配合 `rapp/serve.py` 里对 `charts` 的延迟导入（matplotlib 只在真要出图时才导），
  打包版的启动时间是 **2 秒左右**。
- **打包后没有控制台窗口**，所以程序会把自己的输出接到日志文件
  （`rapp/app.py` 的 `_redirect_output`）。Windows 上 `sys.stdout` 是 `None`，
  不接的话第一句 `print` 就会把程序打死。
- **脚本里可以放心写中文，但得保证 stdout 是 UTF-8**。Windows 的 `stdout` 默认按
  本地代码页编码（英文系统是 cp1252），`packaging/build.py` 第一句
  `print("平台：…")` 就会 `UnicodeEncodeError` 把构建打死 —— 第一次发版就是这
  么挂在 Windows 上的（mac 天生 UTF-8，本地怎么测都是绿的）。两道保险都别拆：
  `build.py` / `analyze.py` 开头的 `sys.stdout.reconfigure(encoding="utf-8")`，
  以及 workflow 里的 `PYTHONUTF8: "1"`（它连子进程一起管）。
- **打包后 Windows 上 `sys.stdout` / `sys.stderr` 是 `None`，不是空流**。任何一句
  `print`、任何 `.isatty()` 都会当场抛 `AttributeError` —— 而且可能发生在**导入
  阶段**（`rapp/report.py` 模块级要判断终端支不支持颜色就是），比 `app.py` 里
  负责把输出接到日志的 `_redirect_output()` 还早，等不到它救命。v0.1.2 的
  Windows 包一启动就弹窗，就是这么来的。护栏放在 `rapp/__init__.py`（所有入口
  都要先过包初始化，一处管住全部），`tests/test_no_console.py` 盯着它别改回去。
- **别直接调 `subprocess`**：窗口模式下 Windows 会给每个子进程开一个新的控制台
  窗口。而这个程序一分析视频就反复调 ffmpeg（取单帧、解遥测、编 HUD），于是
  看板上每点一下就闪一个黑框又立刻消失（用户实测反馈"很烦"）。全部走
  `rapp/subproc.py` 的 `run()` / `popen()`，它们带 `CREATE_NO_WINDOW` —— 这个
  标志**只在 Windows 上生效，macOS 上漏了也看不出来**，所以
  `tests/test_subprocess_hygiene.py` 专门盯着"有没有人绕过它"。
- **Windows 的文件选择框必须挂在 owner 窗体上**（`$d.ShowDialog($f)`，不能是空的
  `ShowDialog()`），否则对话框会躲在浏览器后面：那个进程既没控制台、也没前台窗口
  可依附，Windows 就不会把它激活到最前面，用户看到的就是"点了没反应"（v0.1.3
  实测）。那个 owner 窗体必须 `TopMost`，测试里也有一条盯着它。
- **HUD 的字体必须真的加载到**，否则整块 HUD 会“字小到看不见”。PIL 在
  `truetype` 失败时会退回**内置位图字体**（固定 11 px、不能缩放）—— 不报错、
  不告警，只是字变小了，所以要特别小心。v0.1.4 的 Windows 包就是这么翻车的：
  候选表里全是 mac / Linux 的路径。现在按平台分开列（Windows 用
  `%WINDIR%\Fonts`，不写死 C:），找不到还会扫字体目录，实在不行也退到**可缩放**的
  `load_default(size=…)`。每次出片会先打印一行选中的字体，排问题先看那行：
  `HUD 字体：正文 xxx ／ 数字 xxx`；`tests/test_hud_fonts.py` 盯着这条底线。
- **字体是打进包里的**（`packaging/build.py` 下到 `packaging/fonts/`，spec 再塞进
  包内 `fonts/`）。用的是 **Noto Sans SC + Noto Sans Mono**：SIL OFL 1.1 授权
  允许随程序分发 —— **微软雅黑 / Consolas 不行**，那是微软的专有字体，授权不允许
  跟着别人的程序走。自带的好处是不管用户机器上装了什么，输出都一样
  （“在 mac 上测过”就等于“Windows 上也是这样”）。
  `packaging/fonts/LICENSE-OFL.txt` 是必须随字体附上的授权原文，**删它之前先看条款**。
- 字体走 **jsDelivr** 下（多个镜像域名挨个试）：实测主域名 `cdn.jsdelivr.net`
  在国内 DNS 直接失败，而 `raw.githubusercontent.com` 也連不上 —— 但
  `fastly.jsdelivr.net` 很快。（GitHub 的 Release 附件走
  `objects.githubusercontent.com`，那个是通的，可以当备用方案。）
- **资源路径**：包里的 ffmpeg 在 `sys._MEIPASS/bin`，用户数据（最近打开过的视频、
  日志）在系统的用户数据目录 —— `.app` 是只读的，不能往自己里面写。
  这些分支都在 `rapp/app.py` 开头那几个函数里。

## 附录：内部原理

> 这一节讲"**为什么这么算**"。想改代码、或者想弄明白数字是怎么来的，看这一节；
> 只想用车的话跳过就行 —— 上面 [怎么读这些数据](#怎么读这些数据) 已经讲清楚
> 每个数字代表什么了。

### 1. 遥测提取

GoPro 把遥测以 **GPMF** 格式塞在 MP4 的 `gpmd` 轨道里。它是一种规整的嵌套二进制格式，
每层都是同一个信封：

```
┌──────────┬────────┬──────────┬────────────┬──────────────┐
│ 4 字节名 │ 1 字节 │ 1 字节   │ 2 字节     │ N 字节       │
│ "ACCL"   │ 类型码 │ 单元大小 │ 重复次数   │ 数据载荷     │
└──────────┴────────┴──────────┴────────────┴──────────────┘
载荷长度 = 单元大小 × 重复次数，整个元素补齐到 4 字节边界
```

下面这几条是**拿真实 HERO11 文件逐字节核对出来**的，网上不少文档和第三方实现
在这里是错的，照抄会一个流都解不出来：

| 事实                                                                   | 常见误解                                                                        |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 容器的类型字节是 **`0x00`**                                    | 很多文档写 `'?'`。写错会导致所有流都解不出载荷                                |
| 每个元素都**补齐到 4 字节**                                      | 漏掉这一步，从第二个元素起全部错位（`"Accelerometer"` 13 字节后补了 3 个 0）  |
| `SCAL` 是**逐分量除数**，如 GPS 的 `[1e7,1e7,1000,1000,100]` | 老文档写的是 `(分子,分母)` 数对。按数对解会得到全错的 `[1,1]`               |
| `GRAV` 被归一化到 **±1**（单位是 g），不是 m/s²              | 按 m/s² 检查幅值会误判成"数据异常"                                             |
| `STMP` 是**本块第一个采样点**的时刻                            | 当成"最后一个采样点"会让整条时间轴偏几百毫秒，HUD 对不上画面                    |
| 流名取自**载荷的 4CC**（`ACCL`/`GPS5`…）                    | `STNM` 里装的是描述文字，如 `"GPS (Lat., Long., Alt., 2D speed, 3D speed)"` |
| `STMP` 是 uint64（HERO11）                                           | 老固件是 uint32，71.6 分钟会回绕，仍需兼容                                      |

还有一个坑不在格式里而在 ffmpeg：`-map 0:m:handler_name:"GoPro MET"` 会因为
handler_name 实际带**尾部空格**（`"GoPro MET  "`）而匹配不到，必须退回按轨道索引取。

`rapp/gpmf.py` 负责把这些翻译成 numpy 数组和统一的时间轴。各个传感器流共用一个
**以录制开始为原点**的时间轴（不做归零），这样加速度计和 GPS 之间不会有相对偏移 ——
摄像头开始采集各个传感器的时间本来就有先后（实测加速度计从 0.024 s 开始、
GPS 从 0.116 s 开始）。

### 2. G 值提取（这一步决定了 G 值对不对）

加速度计给出的是**相机坐标系**下的三轴加速度，但我们要的是**赛车坐标系**下的
纵向 / 横向加速度。有两件事要解决：**先把重力扣掉**，再把剩下的加速度**投影到车的
运动方向上**。

#### 第 1 步：扣掉重力

用 GoPro 自己记录的 `GRAV` 流（59.94 Hz，单位向量）逐时刻扣。

**为什么逐时刻比"整场定一个固定重力方向"好**：`GRAV` 是相机自己融合出来的方向，
它跟着相机一起转。所以即使相机在录制中途被人碰了一下、支架有弹性、或传感器温漂，
它都能自动跟上 —— 而固定方向的做法会把那一次扰动**永久**留在后半段数据里。

实测纵向 G 的整圈均值是 **+0.0003 g / −0.017 g**（两段素材）。跑完一圈速度守恒，
纵向均值**必须为 0** —— 这就是为什么要逐时刻扣。

> **踩过的大坑：`GRAV` 和 `ACCL` 根本不在同一个轴系里。**
>
> 直接 `acc - g·GRAV` 是**错的**。实测在车辆静止的窗口里，`mean(ACCL)` 指向 +X
> 而 `mean(GRAV)` 指向 +Y，两者夹角 **82°**。
>
> 真实关系是：**`GRAV` 把 `ACCL` 的前两个分量对调了**。注意这是一个
> **转置**（det = −1），**不是旋转** —— 所以「求一个旋转矩阵」（SVD / Kabsch）
> 从原理上就找不出它，必须枚举符号置换。用干净的静止窗口验证，吻合到 **0.3°** 以内。
>
> **根因**：GPMF 规范要求每条流用 `ORIN` / `ORIO` 声明自己的轴序。这份 HERO11 文件里
> `ACCL` / `GYRO` 明确写着 `ORIN="ZXY"`（即每行分量依次是 Z、X、Y），而 `GRAV` 没有 `ORIN`。
> 我们的解析器之前**完全没有读这个字段**，等于默认所有流都是 XYZ。
>
> 现在的做法不写死映射：枚举全部 **48 个带符号置换**，用物理判据自动挑 ——
> 正确的换轴扣完重力后，剩下的动态加速度模长应该与 GPS 独立算出的
> $\sqrt{(\mathrm{d}v/\mathrm{d}t)^2 + (v\omega)^2}$ 高度相关，**且两者量级接近**。
> 错误的换轴会在数据里留下 1 g 以上的虚假"重力残差"。实测两段素材各自独立地
> 选出同一个映射（$r=0.84/0.71$，模长比 $1.06/1.02$），次优解的量级比就跳到 1.2 以上。

重力大小由 $g = \overline{\vec a \cdot \hat u}$ 求得（在行驶样本上取均值）——
赛道是平的，竖直方向的动态分量在一圈里平均为零。这一步顺带把加速度计的标度误差
自动校掉（实测 9.84~9.90 m/s²）。

#### 第 2 步：投影到**速度坐标系**，不是固定车身轴

**这一步是整个项目最深的坑。**
卡丁车漂移时侧滑角 $\beta$ 在 ±20~30° 之间变化，所以那个固定的"纵向轴"测到的
根本不是 $\dot v$，而是

$$
a_{纵,车身} = |A|\cdot\sin(\beta-\bar\beta)
$$

被峰值 ±15 m/s² 的横向加速度调制。实测它与 GPS 求导的相关性逐圈只有
**−0.38~+0.10**（等于噪声），而 G-G 图上的纵向形状则完全是假的。

正解是把平面加速度矢量投影到**速度方向**上：

$$
\hat A = \frac{\vec a_{水平}}{|\vec a_{水平}|},\qquad
\phi = \operatorname{atan2}(v\omega,\ \dot v),\qquad
a_{纵} = |A|\cos\phi,\quad a_{横} = |A|\sin\phi
$$

|    | 投影方式             | 纵向 r（逐圈中位）   | 纵向斜率 | 横向 r          |
| -- | -------------------- | -------------------- | -------- | --------------- |
| 旧 | 固定车身轴           | **−0.067** ✗ | −0.12   | 0.955           |
| 新 | **速度坐标系** | **+0.919** ✓  | +1.11    | **0.991** |

- $|A|$ 来自 IMU：**矢量模长不受坐标系选择影响**（实测与 GPS 的 $|A|$ 相关性 0.852）
- $\phi$ 来自 GPS：无积分、不漂移

> **为什么不干脆用陀螺仪积分出航向**：积分会漂移。866 秒后偏航误差累积到几十度，
> 实测后几圈会重新退化。而 $\phi$ 完全由 GPS 给出，代价是带宽只有约 1 Hz ——
> 方向的快变部分丢失，但**幅度**仍由 IMU 以 200 Hz 提供，
> 而侧滑角本身是按"秒"变化的慢量。

> **试过但没用上的东西**：`GRAV`（59.94 Hz）、`CORI` / `IORI`（四元数，`IORI` 虚部
> 仅 ±0.098，说明**水平锁定确实开着**）。`GRAV` 已经用在默认路线里扣重力了。
> 但**没有**用它来做姿态积分：`GRAV` 太慢（车身绕水平轴平均 22°/s，`GRAV` 只有 3.4°/s），
> 跟不上卡丁车的抖动。所以当前的用法是「只要方向、不要动态」，正好避开了它的短板。

#### 怎么验证纵向 G 的幅度对不对

**积分守恒**是最硬的判据：一圈之内，纵向加速度的积分必须等于速度的变化量。

$$
\int_0^{T_{圈}} \max(a_{纵},0)\,\mathrm{d}t \;=\; \sum \max(\Delta v, 0)
$$

实测两段素材的比值都在 **0.8~1.1**，说明幅度可信。这条判据同时能抓出
"存在不应有的直流偏置"——偏置会让左式和右式对不上。

#### 峰值 G 一律先按时间平滑 1 秒

**裸信号的单点极值不能用来比车。** 实测 `GX010047` 全场最大的"加速"是 **+1.18 g**，
出现在**车速 0.0 km/h** 的时候 —— 那是二冲程发动机怠速把车抖出来的，
属于 $E|A+噪声| > |A|$ 的噪声底效应，和驾驶动作毫无关系。

所以报表 / 看板里所有"峰值"指标（单圈峰值横 G、峰值刹车、峰值加速、弯道最大横 G、
HUD 刻度）**统一按时间平滑 1 秒后再取极值**（`imu.PEAK_SMOOTH_S`）。

- 平滑窗口必须按**时间**算，不能按距离 —— 距离网格上同样 1 米的窗口，
  在 20 km/h 和 90 km/h 处对应的时间差 4 倍以上，平滑力度根本不一致
- 1 秒既能压掉尖峰，又比卡丁车最短的加速/刹车段（2~3 秒）短，不会抹掉真实峰值

效果对比（`GX010047` 第 5 圈）：峰值刹车 G 从 **1.87 → 0.89**。

#### 想横向比车？看「速度增量」

`速度增量` = 一圈内所有正 $\Delta v$ 之和，单位 m/s。它是**唯一一个有精确物理答案**
的驾驶强度指标（就是上面那条积分恒等式的右端），不受 G 值幅度误差影响。

同一赛道、同一天的两台车实测：

|            | 270cc 四冲程 | Rotax 二冲程 | 倍数            |
| ---------- | ------------ | ------------ | --------------- |
| 速度增量   | 33~37 m/s    | 61~76 m/s    | **2.0×** |
| 峰值加速 G | 0.26~0.34    | 0.53~0.83    | **2.0×** |
| 峰值刹车 G | 0.42~0.67    | 0.60~0.94    | 1.4×           |
| 峰值横向 G | 1.34~1.51    | 1.31~1.61    | 相当            |

横向 G 两者相当（同一条胎、同一套走线），纵向差一倍 —— 这才符合"马力差得多、
轮胎一样"的物理直觉。**如果只看裸信号的单圈最大 G，这个结论会被噪声盖掉。**

#### 走错过的路（结论仍然成立，别再走回去）

> **坑一：整场加速度均值当重力。** 它的前提是相机全程没被移动过，而这份素材恰恰不满足 ——
> 行驶结束（约 640 s）后骑手把相机取了下来，朝向变了 43°~123°。把那些样本混进平均值，
> 平均矢量会被"拉短"，实测只剩 **6.28 m/s²**（真实 9.88）。后果是重力被低估 36%，
> 纵向 G 整体偏移 **−0.4 g**，G-G 图整个歪掉。
> 自查方法：看 `|mean(acc)|` 是否接近 9.8，明显偏小就说明相机被动过。
>
> **坑二：把两个 GPS 参考量一起做三元回归**
> （$\vec a = \dot v\,\hat e_{纵} + v\omega\,\hat e_{横} + \vec g$）。看似优雅，
> 但 $\dot v$ 这一列是**噪声远大于信号**的：实测噪声 0.77 m/s²、信号标准差只有 1.14 m/s²，
> 信噪比约 1.5。弱噪的列会把解带偏 —— 实测算出的重力方向偏了 **49°**，
> 纵向 G 出现 −0.52 g 的直流。而跑完一圈速度守恒，纵向均值必须为 0，
> 所以这个值本身就是"不可能存在"的 —— **物理约束是最好的 debug 工具**。
>
> **坑三：用纵向参考 $\dot v$ 定"哪边是车头"。** 信噪比只有 1.5，判错了就会把
> 横向 G **整体左右翻转** —— 实测与 GPS 的相关性从 +0.90 变成 −0.90，G-G 图左右镜像。
> 正解是纯矢量代数，不要靠相关性定符号。
>
> **坑四：纵向一致性不能在全样本上评估。** 卡丁车转弯时侧滑角很大：
>
> $$
> a_{纵} = \dot v\cos\beta \;-\; v\dot\beta\sin\beta \;-\; v\omega\sin\beta
> $$
>
> 最后一项在漂移时能到 ±0.8 g，会把直线段的真实相关性淹掉（全样本算出来甚至是负的）。
> 必须先筛出 $\omega \approx 0$ 的直线段。
>
> **坑五：只保留 `det=+1` 的旋转矩阵去搜轴变换。** 这会把正确答案（转置，$\det=-1$）
> 直接排除掉，实测为此多花了一整轮排查。

#### 已知残留误差

- **幅度在 ±10% 量级**（实测逐圈斜率 1.04~1.41）。根源是参照量本身：
  GPS 的 $v\omega$ 由强平滑后的位置算出，峰值被衰减约 5~10%，于是方向偏"纵向"。
  横向通道同样能看到 0.90~0.96 的斜率，可以佐证是参照量而非本模块的问题。
- **方向带宽只有约 1 Hz**：快变部分的细节来自 IMU 的幅度，不是方向。
- 极低速段（$|A|<3$ m/s²）IMU 的幅度有约 1.5 倍正向偏置（噪声底，
  $E|A+噪声|>|A|$），会让出场圈起步的抖动、以及**停车怠速时的发动机振动**虚高。
  所以"单圈最大 G"这类极值指标要慎用。
- **`GX010046` 第 7~10 圈的纵向 G 会突然变差**（逐圈 $r$ 从 0.91 掉到 0.82，
  单圈峰值从 0.5 g 涨到 1.0~1.3 g）。怀疑是录制中途相机发生过一次微小移位，
  但尚未查证。对照证据：`GX010047` 全程没有这个现象。

#### 滤波：为什么扣重力前必须先低通

卡丁车没有悬挂，200 Hz 加速度计里混着几十 m/s² 的振动尖峰。直接拿原始数据做
相关性评估，真实驾驶信号会被噪声完全淹没 —— 实测同一份数据，
不滤波时一致性 0.09，先低通是 0.85。

最后输出时再做一次 7 Hz 零相位低通。卡丁车的转向/刹车动作在 0~5 Hz，
而振动能量主要在 10~50 Hz，切在 7 Hz 既保住刹车动作的陡峭前沿又压掉振动。

#### 关于 `CORI` / `IORI` 流（暂未使用）

这份 HERO11 文件里还有 `CORI`（相机朝向四元数）和 `IORI`（图像朝向四元数，
虚部只有 ±0.098，说明**水平锁定是开着的**）。

当前实现**没有用**它们 —— 它们解决的是"绝对姿态"问题，而我们已经用更省的办法
拿到了需要的东西（重力方向由 `GRAV` 给，运动方向由 GPS 给）。

**记录在案，供以后做完整 AHRS 时使用** —— 那时它们是唯一的绝对姿态基准。

### 3. 圈线识别

关键认识：**赛道上任意一点都可以当起终点线**，圈速就是"同一位置连续两次经过之间的
时间"。所以只要那个点每圈都会被经过一次，算出来的圈速就是真实圈速。

真正要解决的是三个问题：

- **哪些点不安全？** 赛道在自己附近拐回来（发夹弯的两条直道只隔几米）时，
  一条直线会被穿过两次。→ 用"偏僻度"衡量：这个点离**同一圈里其它部分**的赛道最近有多远。

  > 这里有个隐蔽的坑：如果判据写成"时间上相隔较远的点"，那么**下一圈的同一个位置**
  > 也会被算进来 —— 而它和当前点的距离本来就是 0（跑的是同一条线），
  > 于是所有候选点的偏僻度都变成 0，筛选彻底失效。必须限定在"同一圈内"。
  >
- **在哪一圈撒候选点？** 不能直接取最后一段。卡丁车练习常以停车收尾，
  实测某次录制的最后 53 秒里车是静止的（全程 25% 的时间速度低于 1 m/s），
  在那段上撒点只会撒出一堆相距一两米的点。→ 滑窗找**同样时长内实际行驶距离最长**
  的那一段。圈时本身用轨迹的**自相关函数**估计（实测 52.8 s，官方 52.5 s）。
- **这个点切出来的圈对不对？** 三个硬判据：每圈时长在 8~300 s 之间、
  圈时的变异系数不超标、**每圈行驶距离的变异系数不超标**。
  第三条最直接：一旦漏穿或多穿，每圈距离会变成半圈或两圈，离散度立刻爆掉。

过线时刻用线性插值定位（找带符号距离的零点）。10 Hz、15 m/s 下相邻两点相隔约 1.5 米，
插值精度在厘米级。但**圈速的物理分辨率大约在 0.1 秒量级** —— 民用 GPS 就是这个水平。

#### 圈与圈之间按"中心线弧长"对齐，不是按里程

这是踩过的一个深坑。不同圈的行驶里程能差近十米（走线宽窄 + GPS 噪声）。
如果按"各自累计里程"对齐，那么**同一个距离值在不同圈对应的赛道位置并不相同**，
末端能错开小半个弯。后果是 delta 曲线在终点附近冒出**负值** ——
看起来"这一圈比最快圈还快"，物理上不可能。

修法是：先用各圈的平均走线得到一条**参考中心线**，再把每圈投影到这条中心线上，
改按中心线的弧长对齐。这样每圈覆盖的都是同一个赛道长度，才真正可比。
修完之后，每圈在终点处的 delta 就等于它和最快圈的圈时差（残差 < 0.1 s）。

> 另外还有个更早的坑：网格长度取中位数会让比网格短的圈被 `np.interp`
> 在末端**钳制**（时间停止增长），比网格长的圈被**截断**（走不完全程），
> 两者叠加同样会造出负的末端 delta。
