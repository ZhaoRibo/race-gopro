# race-gopro —— 从 GoPro 视频里挖出专业赛车遥测

用 GoPro 拍卡丁车练习，然后从这里拿到：

- **圈速**：每圈用时、最快圈、平均圈、标准差
- **分段**：3 个 sector 的成绩，以及"理论最佳圈"（各分段历史最好之和）
- **G 值**：纵向（加速/刹车）和横向（转向）加速度，200 Hz 采样
- **弯道分析**：每个弯的顶点速度、等效半径、刹车点位置及其一致性
- **图表**：速度—距离曲线、G-G 摩擦圆、赛道俯视图、圈间 delta 曲线
- **交互式网页看板**：上面所有内容，可交互
- **带 HUD 的叠加视频**：像转播那样把速度/G 值/圈速烧进画面

数据来源不是"猜"的，而是 GoPro 视频文件里一条**独立的元数据轨道**：

```
GX010123.MP4
├── 视频轨   H.265 / H.264
├── 音频轨   AAC
└── gpmd      ← 就是它。GPS 10~18Hz + 加速度计/陀螺仪 200Hz
```

RaceChrono、Telemetry Overlay 这些专业圈速软件读的也是这条流。

## 快速开始

```bash
# 1. 装依赖（只需要做一次）
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 2. 先自检一下环境和算法有没有问题
.venv/bin/python analyze.py --selftest

# 3. 分析你的视频
.venv/bin/python analyze.py ~/Movies/GX010123.MP4

# 4. 想要带 HUD 的叠加视频（耗时较长，建议先只做一段）
.venv/bin/python analyze.py ~/Movies/GX010123.MP4 --overlay --overlay-range 60,180
```

没有视频也能先看效果：

```bash
.venv/bin/python analyze.py --demo
```

会生成一条合成赛道的数据，把整条输出链路（报表、图表、看板、HUD 视频）都跑一遍。

结果都在 `out/<视频文件名>/` 目录里。

## 拍摄时要注意的事

这几条直接决定数据能不能用，比后期任何处理都重要：

| 事项 | 说明 |
|---|---|
| **相机必须刚性固定在车身上** | 装在前整流罩、座椅后方都行。**绝对不要用头盔支架** —— 相机随头部转动，等于安装角一直在变，G 值就没法算了。 |
| **必须开启 GPS** | HERO11 默认开启。录制时要在室外、起步前给相机 30 秒以上搜星时间，否则前几十秒没有轨迹。 |
| **不要用剪辑软件重新导出** | 任何转码（GoPro Quik、剪映、Final Cut）都会把 `gpmd` 元数据轨丢掉，剩下的只有画面。要分析就必须用相机导出的**原始 MP4**。 |
| **镜头朝向尽量摆正** | 程序会自动标定安装角，歪 20° 以内都能算准；歪太多会降低精度。 |
| **长视频会分段** | GoPro 录久了会把文件切成 `GX01xxxx.MP4` 多段，每段的遥测时间轴都从 0 开始，不能直接拼。先合并：<br>`printf "file '%s'\n" GX01*.MP4 > list.txt`<br>`ffmpeg -f concat -safe 0 -i list.txt -c copy merged.MP4` |

```
├── charts/                 图表
│   ├── lap_times.png
│   ├── speed_trace.png
│   ├── delta.png
│   ├── gg_diagram.png
│   ├── track_map.png
│   └── corner_apex.png
└── tables/                 数据表
    ├── laps.csv
    ├── corners.csv
    ├── laps_aligned_speed.csv
    ├── laps_aligned_glat.csv
    ├── telemetry.csv
```

**先看 `dashboard.html`。** 它是唯一入口，故意放在最外层 —— 结论、图表、明细表
都在这一页里，页尾还有指向下面那些文件的快捷入口，不用自己翻目录找。

之所以把图表和数据表分到子目录：一次分析会产出十几个文件，平铺在一层里
你每次都要在一堆 CSV 中间找那张想看的图。分开之后，"想发朋友圈"去 `charts/`，
"想自己做透视表"去 `tables/`，各取各的。

### 数据表 `tables/`

| 文件 | 内容 |
|---|---|
| `telemetry.csv` | 全场逐点数据：时间、经纬度、速度、航向、纵向 G、横向 G。可以直接拖进 Excel 或 `pandas.read_csv` |
| `laps.csv` | 每圈一行：圈时、与最快圈的差、各分段用时、极速/最慢速、峰值横向/刹车/加速 G、`speed_gain_ms`（速度增量）、`accel_time_pct`（纵向 G 为正的时间占比，**不是全油门**） |
| `laps_aligned_speed.csv` | **距离对齐**的宽表：每一列是一圈，每一行是距起点线 N 米处的速度。想自己画对比图就用它 |
| `laps_aligned_glat.csv` | 同上，横向 G |
| `corners.csv` | 弯道 × 圈 的明细：顶点速度、进出口速度、最大横向 G、刹车点位置 |
| `analysis.json` | 上面所有内容的结构化版本，方便喂给别的工具 |

> 加了 `--no-csv` 就不会生成 `tables/`，看板页尾对应的入口也会自动消失（不会留死链接）。

> **关于 `accel_time_pct`（加速时间占比）**：它统计的是"纵向 G 为正"的时间占一圈的百分比。
> 早期版本把它叫作"全油门时间占比"，**那是错的** —— GoPro 测不到油门开度或刹车压力，
> 而且卡丁车漂移时纵向 G 里混着一项侧滑贡献 $-v\omega\sin\beta$（能到 ±0.8 g），
> 与油门开度没有对应关系。这个字段现在只表示"加速过程占了多久"，别当油门看。
> HUD 里同理不做油门/刹车指示。
>
> **关于峰值 G**：表里所有带“峰值”的列都先按时间平滑了 1 秒（见
> [峰值 G 一律先按时间平滑 1 秒](#峰值-g-一律先按时间平滑-1-秒)）。
> **想要横向比车，看 `speed_gain_ms` 而不是峰值 G** —— 它是有精确物理答案的量。

### 图表 `charts/`

| 文件 | 看什么 |
|---|---|
| `lap_times.png` | 圈速柱状图。柱子高度差 = 你的稳定性 |
| `speed_trace.png` | 速度—距离曲线，所有圈叠在一起。曲线越重合说明走线越一致 |
| `delta.png` | **最有用的一张**。相对最快圈的时间差：曲线上涨 = 正在丢时间，下降 = 正在追回来。一眼看出是哪个弯的问题 |
| `gg_diagram.png` | G-G 图（摩擦圆）。散点外围的那圈红线就是这条轮胎的抓地力极限 |
| `track_map.png` | 赛道俯视图，按速度着色，标出起点线和各弯 |
| `corner_apex.png` | 逐弯顶点速度对比。柱子差得越多，说明这个弯开得越不稳定 |

### 最外层

| 文件 | 说明 |
|---|---|
| `dashboard.html` | 单文件网页看板，**分析的入口**。双击就能打开，数据已内嵌，不需要服务器 |
| `<视频名>_hud.mp4` | 带 HUD 的叠加视频（需要加 `--overlay`） |

**HUD 里显示什么**：左上圈号 / 本圈计时 / 与最快圈的差距 / 最快圈，右上当前速度，
左下纵向 G 指示条（向上绿 = 加速，向下红 = 刹车），中下 G-G 圆盘 + 横向 G 数值，
右下本圈速度曲线对比最快圈。

> **为什么没有油门/刹车指示**：GoPro 测不到油门开度或刹车压力。任何“油门/刹车”
> 都只能从纵向 G 硬换算，而卡丁车漂移时车体系纵向加速度里混着一项
> $-v\omega\sin\beta$（$\beta$ 是侧滑角，能到 ±0.8 g），跟油门刹车毫无关系 ——
> 弯中明明在加油，指示条却在乱跳。与其给个骗人的读数，不如直接显示纵向 G 本身。

## 怎么读这些数据

### 圈速

```
最快圈        52.030  (第 8 圈)
平均圈        52.415
标准差        0.378 s    稳定性: 0.72% —— 很稳定
```

稳定性用**变异系数**（标准差 ÷ 平均圈速）衡量。赛车上的经验值：

| 变异系数 | 含义 |
|---|---|
| < 0.5% | 职业水准，几乎每一圈都一样快 |
| 0.5% ~ 1% | 很稳定 |
| 1% ~ 2% | 较稳定 |
| 2% ~ 4% | 一般，还有提升空间 |
| > 4% | 波动较大，先把节奏稳定下来比找极限更有效 |

出场圈（从维修区出来的第一圈）会自动识别并排除在统计之外，表里用 `*` 标记。

### 理论最佳圈 vs 连续分段最佳

- **理论最佳圈** = 三个分段各自的历史最好成绩之和。
  这个数字**实战中跑不出来** —— 三个分段的最好成绩可能来自三圈互相矛盾的跑法。
- **连续分段最佳** = 相邻三个分段（也就是完整的一圈）用时之和的最小值。
  这个是**真实可达**的：说明你已经在某一圈做到了。

两个数字之间的差距，就是你"知道怎么开但还没连起来"的潜力。

### 弯道表

```
弯 │ 方向 │ 起点 │ 顶点 │ 长度 │ 半径 │ 顶点速度 │ 第5圈 │ 第6圈 │ 速度波动 │ 刹车点离散
2  │   右 │  160 │  170 │   18 │    4 │     27.0 │  26.9 │  27.8 │      1.9 │       21.2
```

- **半径**：由 `a = v²/R` 反推的等效半径。半径 4 m 就是那种一档掉头的发夹
- **顶点速度**：这个弯里速度最低的那一点。卡丁车没有下压力，弯速几乎完全由轮胎摩擦圆决定，所以这是"敢不敢开"最直接的指标
- **速度波动**：同一个弯各圈顶点速度的标准差。**这个数字大 = 这个弯还没形成稳定跑法**，是最该花时间练的地方
- **刹车点离散**：各圈刹车点位置的标准差（米）。偏大说明刹车点每圈都在变，通常是因为在边刹车边找弯心

### Delta 曲线（相对最快圈的时间差）

横轴是距起点线的距离，纵轴是"这一点上比最快圈慢了多少秒"。

**曲线中途出现负值是正常的**：那说明你在赛道的那一段实际上**比自己的最快圈还快**，
只是后来又丢回去了。曲线上升 = 正在丢时间，下降 = 正在追回。
这正是 delta 图的价值 —— 它告诉你时间是在哪个弯丢掉的。

**但在终点处必须为正**：终点处两圈的差距就是圈时差，一圈不可能真的比最快圈还快。
如果你看到终点附近出现负值，那是里程对齐出了问题（本项目早期版本就有这个 bug，
原因见下文"圈与圈之间按中心线弧长对齐"）。

### 圈速和官方计时为什么会有零点几秒的差

圈速是在**自动识别的起点线**上测的。这条线不一定就是官方的计时线，
而赛车场上任意一点的圈速只在"每一圈都跑得一模一样"时才相等。

严格推导一下：设官方计时线在赛道上的位置为 0、自动识别的线在位置 q，
那么自动线的第 k 次到第 k+1 次过线之间的间隔是

$$\Delta t_k = T_k + \big(\text{head}_{k+1} - \text{head}_k\big)$$

其中 $T_k$ 是官方第 k 圈的时间，$\text{head}_k$ 是从官方线跑到位置 q 所用的时间。
所以**只有当你这一段跑得和上一圈一样快时，两者才相等**；
某一圈在 q 之前那段有失误，差值就会表现出来。

实测：同一份数据 9 圈里 8 圈和官方计时差在 **±0.1 s** 以内，
只有一圈差了 0.55 s（就是那一圈在 q 之前那段丢了时间）。

要对齐官方计时，可以从赛道图上读一个官方计时线的坐标用 `--gate 纬度,经度` 指定，
也可以用 `--gate-time 秒` 指定"官方计时线那一次过线发生的时刻"。

### 起点线是怎么选的（以及怎么手动改）

关键认识：**赛道上任意一点都可以当起点线**，圈速就是"同一位置连续两次经过之间的
时间"。所以不存在"唯一正确答案"，但**选得好不好会实实在在地影响结果**：

- 线开在赛道**自己旁边**（另一段赛道的附近）→ 同一圈会被穿两次，圈速直接算错
- 线开在**弯道**上 → 车是斜着走的，过线瞬间的位置抖动更大

工具按下面顺序挑：

1. 沿**连续行驶的那一段**轨迹每 3 米撒一个候选点
   （不能拿整段录制去算 —— 起步前/收车后停车的样本会挤在轨迹同一点，
   算圈时自相关时会把"一圈"那个峰彻底盖住，实测算出 9.9 s，真实是 48.6 s）
2. 每个候选点过**三关**：圈时合理（8~300 s）、圈时一致、**每圈行驶距离一致**
   （最后一条是抓"线开在赛道旁边"最硬的判据：一旦漏穿/多穿，每圈距离会变成
   半圈或两圈，离散度立刻爆掉）
3. 筛掉**偏僻度**不足的（偏僻度 = 这条线离"同一圈里赛道其它部分"最近有多远）
4. 剩下的里**优先选转弯量最小的**（即最靠直道的），同样笔直时取过线最早的

> **为什么先看直道**：赛道上的起点线常规都放在直道上 —— 裁判位、发车格、
> 官方计时线都在直道边。所以"这块直不直"（前后各 30 米内车的总转向角）
> 比"离别的赛道部分有多远"更贴近实际。
>
> 这一条是**用户提的**，实测效果很明显：加上之后圈速标准差从 0.79 s 降到 0.419 s，
> 和官方计时表的 0.42 s 几乎完全一致，且圈数也对上了。

不满意就手动换一条，三种方式（只能用一个）：

```bash
# 1. 先看有哪些候选（按"直道优先"排序，带转弯量 / 偏僻度 / 圈时变异）
python analyze.py 视频.MP4 --list-gates

# 2. 挑第 N 条
python analyze.py 视频.MP4 --gate-index 3

# 3. 用自己的时刻：视频里过线那一帧的秒数（最容易上手，不用读经纬度）
python analyze.py 视频.MP4 --gate-time 200

# 4. 直接给经纬度（从 track_map.png 上读）
python analyze.py 视频.MP4 --gate 22.8754,113.2664
```

手动的线也会自动补上偏僻度 / 圈数 / 圈时变异系数，方便你判断换得对不对。

### G 值

约定：**横向 G 正值 = 左转**（ISO 8855 车辆坐标系），**纵向 G 正值 = 加速、负值 = 刹车**。

横向 G 的绝对值没有太多意义，有意义的是：

- **同一辆车同一条胎，G 越大说明轮胎被用得越充分**。卡丁车通常能到 1.5～2.0 g
- **G-G 图上的形状**：如果数据点集中在一个椭圆里而很少碰到椭圆外沿，说明你离极限还有余量

> **想比车，看「速度增量」而不是峰值 G。** 表格里带"峰值"的列已经自动做过
> 1 秒平滑（[为什么](#峰值-g-一律先按时间平滑-1-秒)），但仍然只是**峰值**；
> 而 `速度增量` 是有精确物理答案的积分量，最能反映马力差异。

G 值的重力扣除用 GoPro 自己记录的 `GRAV` 流逐时刻完成。原理和取舍见
[G 值提取](#2-g-值提取这一步决定了-g-值对不对)。


## 原理（三段核心逻辑）

### 1. 遥测提取

GoPro 把遥测以 **GPMF** 格式塞在 MP4 的 `gpmd` 轨道里。它是一种规整的嵌套二进制格式，
每层都是同一个信封：

```
┌──────────┬────────┬──────────┬────────────┬──────────────┐
│ 4 字节名 │ 1 字节 │ 1 字节   │ 2 字节     │ N 字节       │
│ "ACCL"   │ 类型码 │ 单元大小 │ 重复次数   │ 数据载荷     │
└──────────┴────────┴──────────┴────────────┴──────────────┘
载荷长度 = 单元大小 × 重复次数，整个元素补齐到 4 字节边界
```

下面这几条是**拿真实 HERO11 文件逐字节核对出来**的，网上不少文档和第三方实现
在这里是错的，照抄会一个流都解不出来：

| 事实 | 常见误解 |
|---|---|
| 容器的类型字节是 **`0x00`** | 很多文档写 `'?'`。写错会导致所有流都解不出载荷 |
| 每个元素都**补齐到 4 字节** | 漏掉这一步，从第二个元素起全部错位（`"Accelerometer"` 13 字节后补了 3 个 0） |
| `SCAL` 是**逐分量除数**，如 GPS 的 `[1e7,1e7,1000,1000,100]` | 老文档写的是 `(分子,分母)` 数对。按数对解会得到全错的 `[1,1]` |
| `GRAV` 被归一化到 **±1**（单位是 g），不是 m/s² | 按 m/s² 检查幅值会误判成"数据异常" |
| `STMP` 是**本块第一个采样点**的时刻 | 当成"最后一个采样点"会让整条时间轴偏几百毫秒，HUD 对不上画面 |
| 流名取自**载荷的 4CC**（`ACCL`/`GPS5`…） | `STNM` 里装的是描述文字，如 `"GPS (Lat., Long., Alt., 2D speed, 3D speed)"` |
| `STMP` 是 uint64（HERO11） | 老固件是 uint32，71.6 分钟会回绕，仍需兼容 |

还有一个坑不在格式里而在 ffmpeg：`-map 0:m:handler_name:"GoPro MET"` 会因为
handler_name 实际带**尾部空格**（`"GoPro MET  "`）而匹配不到，必须退回按轨道索引取。

`rapp/gpmf.py` 负责把这些翻译成 numpy 数组和统一的时间轴。各个传感器流共用一个
**以录制开始为原点**的时间轴（不做归零），这样加速度计和 GPS 之间不会有相对偏移 ——
摄像头开始采集各个传感器的时间本来就有先后（实测加速度计从 0.024 s 开始、
GPS 从 0.116 s 开始）。

### 2. G 值提取（这一步决定了 G 值对不对）

加速度计给出的是**相机坐标系**下的三轴加速度，但我们要的是**赛车坐标系**下的
纵向 / 横向加速度。有两件事要解决：**先把重力扣掉**，再把剩下的加速度**投影到车的
运动方向上**。

#### 第 1 步：扣掉重力

用 GoPro 自己记录的 `GRAV` 流（59.94 Hz，单位向量）逐时刻扣。

**为什么逐时刻比"整场定一个固定重力方向"好**：`GRAV` 是相机自己融合出来的方向，
它跟着相机一起转。所以即使相机在录制中途被人碰了一下、支架有弹性、或传感器温漂，
它都能自动跟上 —— 而固定方向的做法会把那一次扰动**永久**留在后半段数据里。

实测纵向 G 的整圈均值是 **+0.0003 g / −0.017 g**（两段素材）。跑完一圈速度守恒，
纵向均值**必须为 0** —— 这就是为什么要逐时刻扣。

> **踩过的大坑：`GRAV` 和 `ACCL` 根本不在同一个轴系里。**
>
> 直接 `acc - g·GRAV` 是**错的**。实测在车辆静止的窗口里，`mean(ACCL)` 指向 +X
> 而 `mean(GRAV)` 指向 +Y，两者夹角 **82°**。
>
> 真实关系是：**`GRAV` 把 `ACCL` 的前两个分量对调了**。注意这是一个
> **转置**（det = −1），**不是旋转** —— 所以「求一个旋转矩阵」（SVD / Kabsch）
> 从原理上就找不出它，必须枚举符号置换。用干净的静止窗口验证，吻合到 **0.3°** 以内。
>
> **根因**：GPMF 规范要求每条流用 `ORIN` / `ORIO` 声明自己的轴序。这份 HERO11 文件里
> `ACCL` / `GYRO` 明确写着 `ORIN="ZXY"`（即每行分量依次是 Z、X、Y），而 `GRAV` 没有 `ORIN`。
> 我们的解析器之前**完全没有读这个字段**，等于默认所有流都是 XYZ。
>
> 现在的做法不写死映射：枚举全部 **48 个带符号置换**，用物理判据自动挑 ——
> 正确的换轴扣完重力后，剩下的动态加速度模长应该与 GPS 独立算出的
> $\sqrt{(\mathrm{d}v/\mathrm{d}t)^2 + (v\omega)^2}$ 高度相关，**且两者量级接近**。
> 错误的换轴会在数据里留下 1 g 以上的虚假"重力残差"。实测两段素材各自独立地
> 选出同一个映射（$r=0.84/0.71$，模长比 $1.06/1.02$），次优解的量级比就跳到 1.2 以上。

重力大小由 $g = \overline{\vec a \cdot \hat u}$ 求得（在行驶样本上取均值）——
赛道是平的，竖直方向的动态分量在一圈里平均为零。这一步顺带把加速度计的标度误差
自动校掉（实测 9.84~9.90 m/s²）。

#### 第 2 步：投影到**速度坐标系**，不是固定车身轴

**这一步是整个项目最深的坑。**
卡丁车漂移时侧滑角 $\beta$ 在 ±20~30° 之间变化，所以那个固定的"纵向轴"测到的
根本不是 $\dot v$，而是

$$a_{纵,车身} = |A|\cdot\sin(\beta-\bar\beta)$$

被峰值 ±15 m/s² 的横向加速度调制。实测它与 GPS 求导的相关性逐圈只有
**−0.38~+0.10**（等于噪声），而 G-G 图上的纵向形状则完全是假的。

正解是把平面加速度矢量投影到**速度方向**上：

$$\hat A = \frac{\vec a_{水平}}{|\vec a_{水平}|},\qquad
\phi = \operatorname{atan2}(v\omega,\ \dot v),\qquad
a_{纵} = |A|\cos\phi,\quad a_{横} = |A|\sin\phi$$

| | 投影方式 | 纵向 r（逐圈中位） | 纵向斜率 | 横向 r |
|---|---|---|---|---|
| 旧 | 固定车身轴 | **−0.067** ✗ | −0.12 | 0.955 |
| 新 | **速度坐标系** | **+0.919** ✓ | +1.11 | **0.991** |

- $|A|$ 来自 IMU：**矢量模长不受坐标系选择影响**（实测与 GPS 的 $|A|$ 相关性 0.852）
- $\phi$ 来自 GPS：无积分、不漂移

> **为什么不干脆用陀螺仪积分出航向**：积分会漂移。866 秒后偏航误差累积到几十度，
> 实测后几圈会重新退化。而 $\phi$ 完全由 GPS 给出，代价是带宽只有约 1 Hz ——
> 方向的快变部分丢失，但**幅度**仍由 IMU 以 200 Hz 提供，
> 而侧滑角本身是按"秒"变化的慢量。

> **试过但没用上的东西**：`GRAV`（59.94 Hz）、`CORI` / `IORI`（四元数，`IORI` 虚部
> 仅 ±0.098，说明**水平锁定确实开着**）。`GRAV` 已经用在默认路线里扣重力了。
> 但**没有**用它来做姿态积分：`GRAV` 太慢（车身绕水平轴平均 22°/s，`GRAV` 只有 3.4°/s），
> 跟不上卡丁车的抖动。所以当前的用法是「只要方向、不要动态」，正好避开了它的短板。

#### 怎么验证纵向 G 的幅度对不对

**积分守恒**是最硬的判据：一圈之内，纵向加速度的积分必须等于速度的变化量。

$$\int_0^{T_{圈}} \max(a_{纵},0)\,\mathrm{d}t \;=\; \sum \max(\Delta v, 0)$$

实测两段素材的比值都在 **0.8~1.1**，说明幅度可信。这条判据同时能抓出
"存在不应有的直流偏置"——偏置会让左式和右式对不上。

#### 峰值 G 一律先按时间平滑 1 秒

**裸信号的单点极值不能用来比车。** 实测 `GX010047` 全场最大的"加速"是 **+1.18 g**，
出现在**车速 0.0 km/h** 的时候 —— 那是二冲程发动机怠速把车抖出来的，
属于 $E|A+噪声| > |A|$ 的噪声底效应，和驾驶动作毫无关系。

所以报表 / 看板里所有"峰值"指标（单圈峰值横 G、峰值刹车、峰值加速、弯道最大横 G、
HUD 刻度）**统一按时间平滑 1 秒后再取极值**（`imu.PEAK_SMOOTH_S`）。

- 平滑窗口必须按**时间**算，不能按距离 —— 距离网格上同样 1 米的窗口，
  在 20 km/h 和 90 km/h 处对应的时间差 4 倍以上，平滑力度根本不一致
- 1 秒既能压掉尖峰，又比卡丁车最短的加速/刹车段（2~3 秒）短，不会抹掉真实峰值

效果对比（`GX010047` 第 5 圈）：峰值刹车 G 从 **1.87 → 0.89**。

#### 想横向比车？看「速度增量」

`速度增量` = 一圈内所有正 $\Delta v$ 之和，单位 m/s。它是**唯一一个有精确物理答案**
的驾驶强度指标（就是上面那条积分恒等式的右端），不受 G 值幅度误差影响。

同一赛道、同一天的两台车实测：

| | 270cc 四冲程 | Rotax 二冲程 | 倍数 |
|---|---|---|---|
| 速度增量 | 33~37 m/s | 61~76 m/s | **2.0×** |
| 峰值加速 G | 0.26~0.34 | 0.53~0.83 | **2.0×** |
| 峰值刹车 G | 0.42~0.67 | 0.60~0.94 | 1.4× |
| 峰值横向 G | 1.34~1.51 | 1.31~1.61 | 相当 |

横向 G 两者相当（同一条胎、同一套走线），纵向差一倍 —— 这才符合"马力差得多、
轮胎一样"的物理直觉。**如果只看裸信号的单圈最大 G，这个结论会被噪声盖掉。**

#### 走错过的路（结论仍然成立，别再走回去）

> **坑一：整场加速度均值当重力。** 它的前提是相机全程没被移动过，而这份素材恰恰不满足 ——
> 行驶结束（约 640 s）后骑手把相机取了下来，朝向变了 43°~123°。把那些样本混进平均值，
> 平均矢量会被"拉短"，实测只剩 **6.28 m/s²**（真实 9.88）。后果是重力被低估 36%，
> 纵向 G 整体偏移 **−0.4 g**，G-G 图整个歪掉。
> 自查方法：看 `|mean(acc)|` 是否接近 9.8，明显偏小就说明相机被动过。
>
> **坑二：把两个 GPS 参考量一起做三元回归**
> （$\vec a = \dot v\,\hat e_{纵} + v\omega\,\hat e_{横} + \vec g$）。看似优雅，
> 但 $\dot v$ 这一列是**噪声远大于信号**的：实测噪声 0.77 m/s²、信号标准差只有 1.14 m/s²，
> 信噪比约 1.5。弱噪的列会把解带偏 —— 实测算出的重力方向偏了 **49°**，
> 纵向 G 出现 −0.52 g 的直流。而跑完一圈速度守恒，纵向均值必须为 0，
> 所以这个值本身就是"不可能存在"的 —— **物理约束是最好的 debug 工具**。
>
> **坑三：用纵向参考 $\dot v$ 定"哪边是车头"。** 信噪比只有 1.5，判错了就会把
> 横向 G **整体左右翻转** —— 实测与 GPS 的相关性从 +0.90 变成 −0.90，G-G 图左右镜像。
> 正解是纯矢量代数，不要靠相关性定符号。
>
> **坑四：纵向一致性不能在全样本上评估。** 卡丁车转弯时侧滑角很大：
>
> $$a_{纵} = \dot v\cos\beta \;-\; v\dot\beta\sin\beta \;-\; v\omega\sin\beta$$
>
> 最后一项在漂移时能到 ±0.8 g，会把直线段的真实相关性淹掉（全样本算出来甚至是负的）。
> 必须先筛出 $\omega \approx 0$ 的直线段。
>
> **坑五：只保留 `det=+1` 的旋转矩阵去搜轴变换。** 这会把正确答案（转置，$\det=-1$）
> 直接排除掉，实测为此多花了一整轮排查。

#### 已知残留误差

- **幅度在 ±10% 量级**（实测逐圈斜率 1.04~1.41）。根源是参照量本身：
  GPS 的 $v\omega$ 由强平滑后的位置算出，峰值被衰减约 5~10%，于是方向偏"纵向"。
  横向通道同样能看到 0.90~0.96 的斜率，可以佐证是参照量而非本模块的问题。
- **方向带宽只有约 1 Hz**：快变部分的细节来自 IMU 的幅度，不是方向。
- 极低速段（$|A|<3$ m/s²）IMU 的幅度有约 1.5 倍正向偏置（噪声底，
  $E|A+噪声|>|A|$），会让出场圈起步的抖动、以及**停车怠速时的发动机振动**虚高。
  所以"单圈最大 G"这类极值指标要慎用。
- **`GX010046` 第 7~10 圈的纵向 G 会突然变差**（逐圈 $r$ 从 0.91 掉到 0.82，
  单圈峰值从 0.5 g 涨到 1.0~1.3 g）。怀疑是录制中途相机发生过一次微小移位，
  但尚未查证。对照证据：`GX010047` 全程没有这个现象。

#### 滤波：为什么扣重力前必须先低通

卡丁车没有悬挂，200 Hz 加速度计里混着几十 m/s² 的振动尖峰。直接拿原始数据做
相关性评估，真实驾驶信号会被噪声完全淹没 —— 实测同一份数据，
不滤波时一致性 0.09，先低通是 0.85。

最后输出时再做一次 7 Hz 零相位低通。卡丁车的转向/刹车动作在 0~5 Hz，
而振动能量主要在 10~50 Hz，切在 7 Hz 既保住刹车动作的陡峭前沿又压掉振动。

#### 关于 `CORI` / `IORI` 流（暂未使用）

这份 HERO11 文件里还有 `CORI`（相机朝向四元数）和 `IORI`（图像朝向四元数，
虚部只有 ±0.098，说明**水平锁定是开着的**）。

当前实现**没有用**它们 —— 它们解决的是"绝对姿态"问题，而我们已经用更省的办法
拿到了需要的东西（重力方向由 `GRAV` 给，运动方向由 GPS 给）。

**记录在案，供以后做完整 AHRS 时使用** —— 那时它们是唯一的绝对姿态基准。

### 3. 圈线识别

关键认识：**赛道上任意一点都可以当起终点线**，圈速就是"同一位置连续两次经过之间的
时间"。所以只要那个点每圈都会被经过一次，算出来的圈速就是真实圈速。

真正要解决的是三个问题：

- **哪些点不安全？** 赛道在自己附近拐回来（发夹弯的两条直道只隔几米）时，
  一条直线会被穿过两次。→ 用"偏僻度"衡量：这个点离**同一圈里其它部分**的赛道最近有多远。

  > 这里有个隐蔽的坑：如果判据写成"时间上相隔较远的点"，那么**下一圈的同一个位置**
  > 也会被算进来 —— 而它和当前点的距离本来就是 0（跑的是同一条线），
  > 于是所有候选点的偏僻度都变成 0，筛选彻底失效。必须限定在"同一圈内"。

- **在哪一圈撒候选点？** 不能直接取最后一段。卡丁车练习常以停车收尾，
  实测某次录制的最后 53 秒里车是静止的（全程 25% 的时间速度低于 1 m/s），
  在那段上撒点只会撒出一堆相距一两米的点。→ 滑窗找**同样时长内实际行驶距离最长**
  的那一段。圈时本身用轨迹的**自相关函数**估计（实测 52.8 s，官方 52.5 s）。

- **这个点切出来的圈对不对？** 三个硬判据：每圈时长在 8~300 s 之间、
  圈时的变异系数不超标、**每圈行驶距离的变异系数不超标**。
  第三条最直接：一旦漏穿或多穿，每圈距离会变成半圈或两圈，离散度立刻爆掉。

过线时刻用线性插值定位（找带符号距离的零点）。10 Hz、15 m/s 下相邻两点相隔约 1.5 米，
插值精度在厘米级。但**圈速的物理分辨率大约在 0.1 秒量级** —— 民用 GPS 就是这个水平。

#### 圈与圈之间按"中心线弧长"对齐，不是按里程

这是踩过的一个深坑。不同圈的行驶里程能差近十米（走线宽窄 + GPS 噪声）。
如果按"各自累计里程"对齐，那么**同一个距离值在不同圈对应的赛道位置并不相同**，
末端能错开小半个弯。后果是 delta 曲线在终点附近冒出**负值** ——
看起来"这一圈比最快圈还快"，物理上不可能。

修法是：先用各圈的平均走线得到一条**参考中心线**，再把每圈投影到这条中心线上，
改按中心线的弧长对齐。这样每圈覆盖的都是同一个赛道长度，才真正可比。
修完之后，每圈在终点处的 delta 就等于它和最快圈的圈时差（残差 < 0.1 s）。

> 另外还有个更早的坑：网格长度取中位数会让比网格短的圈被 `np.interp`
> 在末端**钳制**（时间停止增长），比网格长的圈被**截断**（走不完全程），
> 两者叠加同样会造出负的末端 delta。

## 自检

`--selftest` 会跑两组检查，都不需要真实视频：

**GPMF 二进制解析器**：手工按 GoPro 格式规范构造一段字节流，再喂给解析器，
逐项核对解出来的数值、采样率、单位、缩放是否正确。覆盖了大端序读取、
容器嵌套、`unit_size=0` 的固件差异、以及 71.6 分钟的时间戳回绕。

**G 值提取**：生成一段合成驾驶数据，其中**加速度、重力方向、相机安装角都是已知的**
（故意把相机设成俯仰 −18°、滚转 +6°、偏航 +4° 的歪装，`GRAV` 也加上零点几度的
残余漂移和幅值抖动）。然后：

- 检查识别出的**轴变换是否为恒等**（合成数据里 `GRAV` 与 `ACCL` 本来就同轴系，
  识别错了会立刻暴露 —— 这条能直接抓出轴识别逻辑被改坏）
- 检查解出的重力大小是否接近 9.807
- 把算出的 G 值与真值逐点比对，要求相关系数 > 0.85
- 检查横向 G 的**符号约定**（正 = 左转）是否正确

```
  GPMF 二进制解析器 : 通过 ✓
  G 值提取          : 通过 ✓
```

也可以直接用 pytest：

```bash
.venv/bin/python -m pytest tests/
```

## 已知限制

**说在前面：GoPro 是消费级设备，不是 Racelogic VBOX。**

| 限制 | 影响 | 怎么缓解 |
|---|---|---|
| GPS 只有 10~18 Hz，定位误差 1~3 m | 圈速分辨率约 0.1 s；赛道图上轨迹有可见抖动 | 够用来分析自己的提升趋势，不要拿去和官方计时比 |
| 起步阶段 GPS 可能还没定位 | 开场几十秒没有轨迹，这些圈无法分析 | 录制前给相机 30 秒以上搜星时间 |
| 加速度计有零偏和温漂 | G 值可能有百分之几的绝对误差 | 相对比较（同一场次内的圈与圈对比）是准的 |
| 相机必须刚性固定 | 头盔支架会让数据完全不可用 | 装在车身/整流罩上 |
| 剪辑/转码会丢失遥测轨 | 文件里没有 `gpmd` 流，直接报错 | 只用相机导出的原始 MP4 |
| 卡丁车赛道旁常有建筑 | GPS 多路径误差偏大，个别定位点会飞 | 程序会自动剔除异常定位点并给出警告 |
| 自动识别的起点线不等于官方计时线 | 个别圈的圈速会和官方计时差零点几秒 | 用 `--list-gates` 看候选，再用 `--gate-time 秒` 对到官方计时线 |
| 弯道数量依赖横向 G 峰值识别 | 弯道极密的场地可能多切或漏切 | 调 `rapp/analysis.py` 里的 `CORNER_MIN_SEPARATION` |

另外：卡丁车短赛道的弯道比较密集，程序按"横向 G 超过 0.25 g 且持续 8 米以上"来
划分弯道。特别近的连续弯（比如蛇形弯）可能会被合并成一个，可以把
`rapp/analysis.py` 里的 `CORNER_MAX_GAP` 调小。

## 常见问题

**Q: 报错"没有可用的 GPS 数据"**

录制时没开 GPS，或者视频被转码过。用 `--list-streams` 确认一下文件里有没有遥测轨。

**Q: 报错"没能找到合适的起终点线"**

按提示的三种原因排查。也可以先用 `--list-gates` 看看有哪些候选位置，
再用 `--gate-index N` 或 `--gate-time 秒` 手动指定。

**Q: 圈速明显不对（比如只有实际的一半，或者标准差很大）**

起终点线开在了赛道自己旁边。看 `track_map.png` 上黑线的位置，
如果它靠近赛道的另一段，就用 `--list-gates` 换一条（选“转弯量小、偏僻度大”的）。

**Q: G 值看起来不对 / "G 值一致性" r 很低**

先检查相机是不是刚性固定在车身上（最常见的原因是装在了头盔上）。
其次确认支架没松动。`--selftest` 通过说明算法本身没问题。
另外留意：**单圈最大 G 不可靠**，别拿它下结论 —— 见
[G 值](#g-值) 里的说明。

**Q: HUD 视频要跑很久**

用 `--overlay-range 起,止` 只做你关心的那几圈，或者把 `--overlay-fps` 调到 10。
1080p 下大约是每帧 13 ms，20 分钟的视频（15 fps）大概 4 分钟。
